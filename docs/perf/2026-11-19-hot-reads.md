# Performance audit — hot read paths (migration 0033)

Date: 2026-11-19. Branch: `arena/07d3afb3-fantasy-friends-rec`. Base: `main@57258657` (post PR #34).

## Scope and method

Audit of the read paths behind the Dashboard, Standings, Squad, Next Match, Points,
match detail/history and player-stats screens, following the already-merged
optimizations of PR #29 (auth/read batching) and PR #30 (read consolidation,
scoped live points). All numbers below are **local measurements** against a
disposable PostgreSQL 18 database seeded with a representative league:

- League A: 12 managers, 4 teams, 44 players, **300 approved matches** (~2 seasons
  of weekly play), 1 live match, 2 future fixtures, ~7,500 match events,
  ~6,600 scored player rows, ~3,600 standings-history rows, ~3,600 lineup-history
  rows, 300 finalized lineup snapshots, 20 notifications per manager.
- League B: 6 managers, 10 matches (cross-league isolation checks).

Production metrics were **NOT MEASURED** (no production access was usable; the
Supabase connector's `execute_query` dropped its arguments on every call).
Where production differs from the seed (more leagues sharing the same tables),
the un-indexed per-row costs measured here would be **larger**, not smaller.

Seed/bench tooling (committed under `scripts/`, refuses non-localhost URLs):

```
node scripts/setup-local-integration.mjs            # schema 0001-0033 on a local db
DATABASE_URL=... node scripts/perf-seed.mjs         # representative dataset
DATABASE_URL=... node scripts/perf-bench.mjs before # timings + EXPLAIN plans
DATABASE_URL=... node scripts/perf-dump-golden.mjs before   # parity capture
DATABASE_URL=... node scripts/perf-rpc-parity.mjs   # RPC parity + isolation checks
```

## Baseline findings (before)

| # | Path | p50 | Root cause |
|---|------|-----|-----------|
| 1 | `player_finalized_games_with_logos` (player stats screen) | **513 ms** | Candidate matches were found through the `match_scoring_lineups` view with only a league predicate pushed down: the view's non-finalized branch seq-scanned `match_lineups` and evaluated its RLS policy (3 security-definer function calls per row) for **every lineup row in the database**. Under the function's generic plan, the same view was also re-scanned once per returned match. |
| 2 | Points route JS (default view, polled every 10 s) | **832 ms** | Per points row, the route filtered the **entire league event list**: 6,600 rows × 7,508 events ≈ 49.5M comparisons per request. |
| 3 | `match_events` league-wide read (points route, polled) | **214 ms** | Direct table read with the `is_member(league_id)` RLS policy re-evaluated per scanned row (~25 µs × 7.5k rows). The same read with RLS bypassed: 11 ms. |
| 4 | `fantasy_points_history` read (standings screen) | **23 ms** | Same per-row RLS evaluation over 3.6k rows, plus a sort of the full league history before `LIMIT 200`. |
| 5 | Points page client render | ~2M comparisons | `matches.map(m => rows.filter(r => r.matchId === m.id))` — quadratic grouping on every poll render. |

Measured and found **healthy** (left unchanged): `ff_display_standings` 0.8 ms,
`ff_my_live_match_points` 0.4 ms, `last_game_points` 0.3 ms, `ff_next_match_lineup`
0.3 ms, `ff_squad_deadline` 0.2 ms, dashboard squad read 1.0 ms, dashboard
notifications 0.3 ms, dashboard recent matches 1.4 ms, `recent_fantasy_substitutions`
5-6 ms, `ff_my_latest_display_player_points` 9-15 ms (already optimized in PR #30),
`ff_display_player_points` single-match 2.4-9 ms. The dashboard route's ten reads
are independent and dispatched in one parallel batch (verified by the
read-consolidation tests). Per-mount request counts remain: Dashboard 1,
Standings 1, My Team 2 (PR #29 baselines, still enforced by tests).
Client bundle: 92 chunks, 1.33 MB total, per-route code splitting — no action.

## Changes

1. **Migration `0033_perf_hot_reads.sql`**
   - `player_finalized_games_with_logos` rewritten internally: the candidate
     matches now come straight from `match_lineups` / `finalized_match_lineups`
     with the league **and player** predicates in place (using the existing
     `lineup_league_player_match_idx`), and the final join reads the same two
     base tables per match instead of re-scanning the view. Same signature,
     same parameters, same result columns, same `security invoker` execution,
     same RLS policies applied to the same base tables. The
     `match_scoring_lineups` view and its other (match-scoped, already indexed)
     consumers are untouched.
   - New scoped security-definer readers, following the PR #26/#27 pattern
     (membership verified once inside; revoked from `public`/`anon`; granted to
     `authenticated`):
     - `ff_league_match_events(p_league, p_match default null)` — the exact
       columns the points route selected.
     - `ff_league_points_history(p_league, p_limit default 200)` — history rows
       with the match title/kick-off and profile names already joined, ordered
       by `created_at, id` (the id tiebreak makes the batch-tied order
       deterministic; the direct read never specified one), limit clamped to
       1..500.
   - New indexes, each justified by a measured query:
     - `finalized_match_lineups(league_id)` — the rewritten candidate lookup;
       the table previously had only its `match_id` pkey while growing by one
       row per approved match.
     - `match_events(league_id)` — the league-wide events read; the table had
       only per-match and per-player indexes and grows without bound.
     - `fantasy_points_history(league_id, created_at, id)` — the standings
       history read; lets the ordered scan stop at `LIMIT 200` instead of
       scanning and sorting the league's whole history (also speeds the
       remaining direct read path, which keeps its RLS).
2. **`points/route.ts`** — events are read via `ff_league_match_events`, and the
   per-row event matching is grouped once in a `Map` instead of filtering the
   full league history per row. Response shape unchanged field-by-field
   (including scorer-vs-assist attribution and event order within a player).
3. **`standings/route.ts`** — history is read via `ff_league_points_history`
   and mapped from its flat columns; response shape unchanged.
4. **`points/page.tsx`** — rows grouped per match once in a `Map` before render
   (same output order as the old quadratic grouping).

## Results (local, seeded dataset, warm cache, p50 of 30)

| Path | Before | After | Change |
|------|--------|-------|--------|
| `player_finalized_games_with_logos` | 513 ms | 18.9 ms | **27×** |
| League-wide events read (points route) | 214 ms | 17.5 ms | **12×** |
| Standings history read | 22.9 ms | 1.6 ms | **14×** |
| Points route event matching (JS) | 832 ms | 5.4 ms | **154×** |
| Points route total, default view (DB + route JS) | ≈ 1,145 ms | ≈ 107 ms | **≈ 10×** |

The remaining default-view cost is `ff_display_player_points` itself (~52-84 ms
for 6,600 rows) plus ~3 MB of response payload — both are the screen's contract
(it renders the full league history), so they were left unchanged.

## Parity and safety evidence

- Golden capture of **all 44 players × 3 call variants** (default, small limit
  without breakdown, cursor pagination) before and after the function rewrite:
  byte-identical (`perf-compare-golden.mjs`).
- `ff_league_match_events` / `ff_league_points_history` vs the direct reads they
  replace: identical row sets and column values for a member, empty for a
  non-member (same as RLS), empty cross-league, `42501` for `anon`
  (`perf-rpc-parity.mjs` + integration tests).
- No RLS policy was modified; no grant was widened (new functions are
  `authenticated`-only and membership-checked); no writes, scoring, lineup
  lifecycle, deadline, captain/vice, or approval logic was touched.
- Suites: 229 unit + 90 PostgreSQL integration tests (2 new describe blocks
  covering the scoped reads and the rewritten history function), typecheck,
  build, `audit:sql` (extended with 0033 assertions), 0028/0030 parity scripts —
  all green.

## Remaining limitations / not done (with reasons)

- **Points default-view payload (~3 MB / poll)** — contract-bound; shrinking it
  needs a paginated/product decision, not a drop-in optimization.
- **Per-row RLS cost on other tables** — the same `is_member` pattern exists on
  ~15 policies, but every other hot read is either match-scoped (few rows) or
  already behind a security-definer RPC, so no further change is justified by
  measurements. A future systemic option is rewriting policies into hashed
  subplan form (`league_id in (select ...)`) — deliberately **not** done here to
  keep the security surface untouched.
- **Standings history shows the oldest 200 rows** (`created_at asc limit 200`),
  which for long leagues silently truncates recent matchdays. This pre-exists
  and is preserved as-is (behavior preservation); flagged for a product decision.
- **Production measurements: NOT MEASURED.** Apply migration 0033 on staging
  first and re-check the same routes before promoting.

## Production rollout notes

- Migration `0033_perf_hot_reads.sql` is additive (one `create or replace` of a
  stable function, two new functions, three new indexes, grants, `notify pgrst`).
  It takes no table locks beyond brief `CREATE INDEX` builds on
  `finalized_match_lineups`, `match_events`, `fantasy_points_history` (one index
  entry per existing row; on large `match_events` tables consider running at low
  traffic). No data is rewritten or deleted.
